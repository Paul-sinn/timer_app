# Architecture Decision Records

## 철학
모바일(iOS) 사용자 경험 최우선. 먼저 동작하는 **UI를 더미 데이터로** 완성한 뒤 기능을 붙인다(SDD/TDD를 step별로 강제). 외부 의존성은 Supabase + FastAPI로 단순하게 유지하고, AI 등 부가 기능은 검증된 수요가 생긴 뒤 도입한다.

---

### ADR-001: 네이티브 SwiftUI 선택
**결정**: iOS/macOS를 SwiftUI 단일 코드베이스로 구현하고, 디자인은 Figma에서 먼저 만든 뒤 Figma MCP로 반영한다.
**이유**: 알 부화 애니메이션·화면 꺼짐 방지 등 네이티브 기능이 핵심이고, 모바일 UX 품질이 최우선 목표.
**트레이드오프**: 안드로이드/웹은 포기. 크로스플랫폼 코드 재사용 불가.

### ADR-002: 구현 순서 — UI 우선, 더미 데이터
**결정**: 1단계에서 기능·로그인 없이 프론트엔드 UI만 더미 데이터로 완성하고, 2단계에서 실제 기능을 구현한다.
**이유**: 화면 구조와 UX를 빠르게 확정해 피드백을 받고, 백엔드/로그인 복잡도를 뒤로 미뤄 리스크를 분리.
**트레이드오프**: 초기에는 "보이지만 동작하지 않는" 화면이 존재. Mock/실제 Service 교체 비용 발생.

### ADR-003: 저장소 — SwiftData(로컬) + Supabase(원격)
**결정**: 로컬은 SwiftData, 원격은 Supabase(Auth/Postgres/Storage)로 이원화한다.
**이유**: 오프라인에서도 타이머·컬렉션이 동작해야 하고, 계정/동기화/이미지 저장은 Supabase로 빠르게 확보.
**트레이드오프**: 로컬-원격 동기화 정책을 별도로 설계·관리해야 함.

### ADR-004: 백엔드 분리 — FastAPI
**결정**: 클라이언트가 Supabase에 직접 접근하는 대신, 민감 로직과 (추후) AI 호출은 FastAPI 백엔드를 경유한다.
**이유**: 확률표·부화 검증 등 서버 권위가 필요한 로직과 AI 키를 클라이언트에서 분리.
**트레이드오프**: 서버 운영·배포 비용 추가. 단순 CRUD까지 서버를 거치면 지연 증가.

### ADR-005: AI 기능 보류
**결정**: OpenAI/Gemini 연동 경로(FastAPI 경유)는 설계만 두고 MVP에서는 구현하지 않는다.
**이유**: 당장 핵심 가치는 타이머·부화·컬렉션. AI는 유료 기능 수요 확인 후 도입.
**트레이드오프**: AI 기반 차별화는 출시 시점에 없음.

### ADR-006: 캐릭터 이미지 — Mock 우선
**결정**: 캐릭터 이미지는 직접 제작 예정이므로, 그 전까지 mock 이미지를 동일 자리/규격으로 채워 둔다.
**이유**: 에셋 제작이 UI 진행을 막지 않도록 분리.
**트레이드오프**: 정식 에셋 교체 작업이 추후 필요. 규격(비율/해상도) 사전 합의 필요.

### ADR-007: 인증 — Apple + Google (Supabase Auth)
**결정**: Apple 로그인과 Google 로그인을 Supabase Auth로 연동한다.
**이유**: iOS 정책상 Apple 로그인 필요, Google로 접근성 확보. Supabase가 두 공급자를 일괄 관리.
**트레이드오프**: 자체 이메일/비밀번호 로그인은 범위 외.

### ADR-008: 개발 프로세스 — SDD/TDD step 강제
**결정**: 기능 구현은 스펙→테스트→구현 순서를 step별로 강제(훅으로 관리)하고, 역할을 A(개발)·B(PM/검수)·C(디자인, Figma MCP)로 나눈다.
**이유**: 더미 UI에서 실기능으로 넘어갈 때 품질·검수 일관성 확보.
**트레이드오프**: 초기 진행 속도는 다소 느려짐.
